# ImfOptions Class

## Definition

Namespace: `DataStandardizer.File.InternetMessage`

Options to configure the behaviour of an Internet message reader or writer.

**.NET:**

```csharp
public sealed record ImfOptions
```

**.NET Standard:**

```csharp
public sealed class ImfOptions
```

## Remarks

The default settings for all options ensure behaviour consistent with RFC 5322, RFC 6532, RFC 2045, RFC 2046 and RFC 4155, and with the layout that Apple Mail gives EMLX files, which has no published standard. Each accommodation for common non-compliant input is a separate option, off by default. A writer always writes what the standards allow, so the accommodations affect it only where noted.

| `AcceptBareLineFeed` | `bool AcceptBareLineFeed { get; init; }` | Gets a flag indicating if a bare line feed is accepted as a line break: at the end of a field, in a fold, and as the empty line that ends the header section. RFC 5322 §2.1 requires lines to end in CRLF, and §2.2 allows CR and LF in a field only as part of a fold. When `false` (the default), a bare line feed causes an [`ImfFileException`](ImfFileException.md). A bare carriage return is never accepted. With an [`ImfEntityReader`](ImfEntityReader.md), the same goes for the line breaks of a multipart delimiter (RFC 2046 §5.1.1) and of a quoted-printable body being decoded (RFC 2045 §6.7); when `false`, a delimiter with a bare line feed is content. A writer never adds a bare line feed, but with this option it accepts one in a raw field given to [`ImfHeaderWriter.WriteRawField`](ImfHeaderWriter.md) or [`ImfEntitySource.AddRawField`](ImfEntitySource.md), which it copies as it is. |
| `AllowBinaryTransferEncoding` | `bool AllowBinaryTransferEncoding { get; init; }` | Gets a flag indicating if an [`ImfEntityWriter`](ImfEntityWriter.md) may give a body the `binary` transfer encoding, when it has not been told which to use. It also limits how deeply the values of the property list of an EMLX file nest, and deeper values make the property list one that isn't well formed, as `AllowInvalidEmlxMetadata` describes. |
| `MaxPartCount` | `int MaxPartCount { get; init; }` | Gets the maximum number of entities in a message, not counting the message itself. RFC 2046 sets no limit. This one guards against hostile input. Every part of a multipart entity and every embedded message counts, at any depth. The default is `DefaultMaxPartCount`, and the value must be at least 1. One more entity causes an [`ImfFileException`](ImfFileException.md). |

## Applies to

Targets `netstandard1.1`, `netstandard2.0`, `netstandard2.1`, and `net10.0`.
This type is a `record` on `net10.0`, so `with` expressions work there, and its properties are `init`-only. On the .NET Standard targets it is a plain `class`, and its properties have `set` accessors.
The nullable reference annotations apply to the `netstandard2.1` and `net10.0` builds.
